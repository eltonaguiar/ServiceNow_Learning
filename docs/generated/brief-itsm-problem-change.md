### Fields — critical vs useful vs optional

**Critical** (get these wrong and the module misbehaves; mandatory-ness varies by instance):

- `type` — standard / normal / emergency decides which approvals and which fields appear. Get this wrong and approvals never fire.
- `short_description` — Mandatory; appears in CAB agenda.
- `start_date + end_date` — Drives conflict detection and the change calendar.
- `assignment_group` — Routing and approval targeting.
- `risk + impact` — Feed approval policy; changing them mid-flight can re-trigger approvals.
- `implementation_plan + backout_plan + test_plan` — Required by OOB for normal changes; blank plans are the #1 audit finding.

**Useful:** `cmdb_ci`, change_plan (template), `cab_required`, `conflict_status`, `review_status`

**Optional / nice to have:** unauthorized flag, Justification fields, test/validate dates

**Related lists worth configuring:** Change Tasks, Affected CIs, `Approvers`, `Conflicts`, Affected/Impacted services

## Must know (the 5 facts that unlock the rest)

- Standard change = pre-approved via a template; normal goes through CAB; emergency is the 'break glass' path. Choosing the type is the whole design decision.
- Approvals are sysapproval_approver records created by a flow, not a field.
- A problem is not an incident. Problem = root cause; incident = symptom. Link them, do not merge them.

## Common mistakes

- Building approvals with the legacy Workflow Editor when Flow Designer is the supported path on current releases.
- Approving as the requester's delegate and calling it a two-person control.
- Leaving test_plan blank, then failing an audit.
- Creating standard change templates without a retry/backout path.
