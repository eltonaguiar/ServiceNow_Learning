## Why this module first

The CMDB is the platform's spine: incidents, changes, assets, services, and impact analysis all point at CIs. It is also the module people most often 'set up' without understanding.

## The 60-second orientation

- Primary table: `cmdb_ci`
- Tables that matter: `cmdb_ci`, `cmdb_ci_server`, `cmdb_ci_linux_server`, `cmdb_rel_ci`, `cmdb_ci_service`, `cmdb_ci_service_discovered`, `cmdb_model`, `discovery_status`

### Fields — critical vs useful vs optional

**Critical** (get these wrong and the module misbehaves; mandatory-ness varies by instance):

- `name` — Together with the identification rule, decides whether you create a duplicate CI.
- `sys_class_name` — You must pick the right class at create time; moving class later is painful.
- `install_status / operational_status` — Impact analysis and asset lifecycle depend on them.
- `environment (prod/test/dev)` — Everything downstream (change risk, alerts) assumes it is right.
- `managed_by_group` — Support group routing for CI-related incidents.
- `discovery_source` — Tells you whether a CI is authoritative or hand-typed.

**Useful:** `ip_address`, `fqdn`, `serial_number`, `assigned_to`, `location`, model_id / manufacturer

**Optional / nice to have:** u_* business fields, `support_group`, `comments`

**Related lists worth configuring:** Relationships (cmdb_rel_ci, both directions), `Incidents`, `Changes`, `Assets`, Service offerings

> Mandatory is not a guess. Confirm it: `All > System Definition > Tables & Columns`, pick the table, filter the columns on `Mandatory = true`. The probe script does this for every table below in one run.

## Must know (the 5 facts that unlock the rest)

- Identification rules (CI Identifiers) must be configured before you load data, or you ship duplicates on day one.
- Relationships are bidirectional records (parent/child); both sides matter for impact analysis.
- Class hierarchy is the model: server → linux server → …; put data at the most specific correct class.
- CMDB health = correctness + completeness + compliance. Pick one, prove it, then expand.

## Common mistakes

- Bulk-importing CIs before defining identification rules (creates thousands of duplicates you cannot merge cleanly).
- Using cmdb_ci for everything instead of the proper subclass.
- Treating Discovery as 'just install the mid-server' — without credentials and scope, discovery produces noise.
- Manually creating CIs that discovery will later duplicate.
