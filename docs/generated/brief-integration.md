### Fields — critical vs useful vs optional

**Critical** (get these wrong and the module misbehaves; mandatory-ness varies by instance):

- `Endpoint + HTTP method` — Half of all integration bugs are wrong URL, method, or content-type.
- `Authentication (basic / OAuth 2.0 / API key in header)` — Never hardcode secrets; use Connection & Credential aliases.
- `Headers incl. Content-Type and Accept` — APIs reject silently-wrong content types.
- `Response body parsing (JSON path)` — This is where 'it returned 200 but nothing happened' lives.
- `Timeout + retry policy` — Default timeouts make slow APIs look broken.

**Useful:** MID Server selection, mutual TLS, rate-limit backoff, error handling branch

**Optional / nice to have:** custom logging tables, payload templates

**Related lists worth configuring:** HTTP Methods (sys_rest_message_fn), `Variables`, HTTP Headers, `Authentication`

> Mandatory is not a guess. Confirm it: `All > System Definition > Tables & Columns`, pick the table, filter the columns on `Mandatory = true`. The probe script does this for every table below in one run.

## Must know (the 5 facts that unlock the rest)

- Outbound REST Message = ServiceNow calls out. Scripted REST API = the world calls in. Remote Table = the world's API pretends to be a table.
- Remote Tables are read-only views. If you need writes, use REST + Flow/scripted action.
- Use Connection & Credential aliases so credentials are not in the message body or scripts.
- Check sys_outbound_http_log before blaming the API.

## Common mistakes

- Hardcoding tokens in scripts (leaks into update sets and logs).
- Ignoring the response status: 200-with-error-payload is common.
- Not pinning content-type, then debugging JSON parse errors for an hour.
- Building a remote table for high-volume joins (performance cliff) instead of a scheduled sync.
