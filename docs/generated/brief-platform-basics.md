## Why this module first

Every other module is the same machinery with different tables. Learn the machinery once and each new module costs you about an hour instead of a week.

## The 60-second orientation

- Primary table: `sys_user`
- Tables that matter: `sys_user`, `sys_user_group`, `sys_user_role`, `sys_dictionary`, `sys_db_object`, `sys_app_module`, `sys_hub_flow`, `sys_ws_definition`, `sys_properties`
- Roles to test with: `admin`, `itil`, `snc_internal`

## Breadcrumbs (where to actually click)

1. Filter navigator (top-left, type-anywhere) — your real navigation, faster than clicking menus
2. All > System Definition > Tables & Columns  (sys_db_object + sys_dictionary: the map of everything)
3. All > System Definition > Application Menus  (sys_app_module: why a menu item exists / where it points)
4. All > System Applications > All Available Applications  (what is installed, and what is available to install)
5. All > User Administration > Users  (sys_user: impersonate a persona to see their menus)
6. Profile avatar (top-right) > Impersonate user  (the single most useful learning tool on the platform)

### Fields — critical vs useful vs optional

**Critical** (get these wrong and the module misbehaves; mandatory-ness varies by instance):

- `sys_user.user_name` — Login id; impersonation and approvals hinge on it.
- `sys_user.active` — Inactive users still resolve in history but cannot log in; never delete, deactivate.
- `sys_user_group.name` — Assignment groups are the unit of routing in every ITSM table.
- `sys_dictionary.mandatory` — The real answer to 'which fields are required' — read it, do not guess.

**Useful:** `sys_user.title`, `sys_user.manager`, `sys_user_group.manager`, `sys_user_group.parent`, `sys_properties.value`

**Optional / nice to have:** `sys_user.photo`, `sys_user.preferred_language`

**Related lists worth configuring:** sys_user > Roles, sys_user > Groups, sys_user_group > Members, sys_user_group > Roles

> Mandatory is not a guess. Confirm it: `All > System Definition > Tables & Columns`, pick the table, filter the columns on `Mandatory = true`. The probe script does this for every table below in one run.

## Must know (the 5 facts that unlock the rest)

- A record is a row; a field is a column; a table extends another table (incident extends task, which extends sys_...base).
- Lists are filtered views of a table; a form is one record; a related list is another table filtered to this record.
- Almost everything you see is a record in a table. 'Where does this come from?' is answered by Tables & Columns, not by memory.
- Dev → Test → Prod is a promotion path, not three copies of your homework. Never experiment in prod.

## Common mistakes

- Learning by clicking menus instead of the filter navigator (10x slower, and you never learn the table name).
- Skipping impersonation, so you never see the UI the actual user sees.
- Assuming your instance looks like the docs screenshot — release + plugins + theme all change it.
